# install-vpn.sh — свой VPN «под ключ»

Один файл: кладёте на чистый сервер, запускаете — через минуту готов VPN со ссылками и QR-кодами
для телефонов и компьютеров. Внутри 3x-ui + Xray, протокол VLESS + XHTTP + Reality.
Скрипт сам проверяет, не заблокирован ли IP сервера в России, ставит защиту от подбора пароля
и команду `vpn-check` для диагностики.

## Что нужно

- Сервер за рубежом: **Ubuntu 22.04 / 24.04 или Debian 12**, x86_64 или arm64, от 1 ГБ ОЗУ, доступ root по SSH.
  На сервере не должно быть другого сайта: скрипту нужен порт 2083 и порт 80 (с доменом ещё 443, без домена — 2096).
- По желанию — **домен** (с ним лучше, см. ниже). Домен в Cloudflare — проще всего: скрипт попросит токен
  Cloudflare, покажет ваши домены, вы выберете домен (или впишете поддомен), и A-запись на этот сервер он
  поставит сам. Домен не в Cloudflare — A-запись на IP сервера сделать самим (Proxy выключен, без AAAA).
- Если у хостера есть свой фаервол в панели — открыть TCP 22, 2083 и 80; с доменом ещё 443, без домена — 2096
  (подписка) и порт панели (скрипт его напечатает).

## Установка

На новом сервере под root — две команды:

```bash
curl -fsSL -o install-vpn.sh https://raw.githubusercontent.com/Jodc2/vpn-install/main/install-vpn.sh
bash install-vpn.sh
```

- Нет curl — то же через wget: `wget -O install-vpn.sh https://raw.githubusercontent.com/Jodc2/vpn-install/main/install-vpn.sh`
- Зашли не под root — запускать `sudo bash install-vpn.sh`.
- Не запускайте через `curl … | bash`: скрипт должен лежать файлом — он кладёт свою копию для команд
  `vpn-check` и `vpn-warp`.

Скрипт спросит, есть ли домен: «в Cloudflare» (сам настроит DNS), «не в Cloudflare» или «нет». Без вопросов:
`bash install-vpn.sh --domain vpn.example.com` (с токеном Cloudflare в `CF_API_TOKEN` A-запись создастся сама,
если её нет; запись на другой IP без терминала не трогается) или `bash install-vpn.sh --no-domain`.

В конце он печатает панель (адрес, логин, пароль) и подписки или ссылки для каждого устройства с QR-кодами.
То же сохраняется в `/root/vpn-info.txt`, картинки QR — в `/root/vpn-qr/`. Журнал — `/root/vpn-install.log`.

## С доменом или без

| | С доменом | Без домена |
|---|---|---|
| Маскировка | Reality «steal-oneself»: SNI — ваш домен, тому, кто прощупывает сервер, отдаётся настоящий сайт-заглушка с этого же сервера | Reality под крупный чужой сайт (www.apple.com, www.samsung.com…): скрипт проверяет кандидатов с сервера и берёт самый быстрый |
| Порты | 2083 — VPN, 443 — сайт, панель и подписка, 80 — продление сертификата | 2083 — VPN (как у основного сервера; `--port` — другой), 2096 — подписка, 80 — продление сертификата, случайный — панель |
| В приложения | подписка: обновляется сама | подписка `https://IP:2096/…`: обновляется сама (но при переезде на другой IP — раздать заново) |
| Панель | `https://домен/секретный-путь/` | `https://IP:порт/секретный-путь/` с сертификатом Let's Encrypt на IP; с `--panel-local` — только через SSH-туннель |
| Переезд на другой сервер | клиентам ничего не делать — меняется A-запись | клиентам заново добавить ссылки (restore.sh их печатает) |
| Сертификат | Let's Encrypt на домен, продлевается сам | Let's Encrypt на IP: короткий (~6 дней), продлевается сам каждые ~2–3 дня. Не получен (закрыт порт 80) — подписка только внутри сервера, в QR прямые ссылки `vless://`, панель с самоподписанным сертификатом |

## Что скрипт делает по шагам

1. Проверяет систему и что нужные порты свободны.
2. **Проверяет IP через check-host.net:** открывается ли SSH сервера из России и из Европы. Из России
   закрыт, а из Европы открыт — IP в бане, установка не начинается, на сервер ничего не ставится.
   Открыт не со всех узлов — спрашивает, продолжать ли.
3. С доменом — ставит A-запись в Cloudflare (если дан токен; запись на чужой IP — только с вашего «да»),
   сверяет её и выпускает сертификат Let's Encrypt (acme.sh, sha256 закреплён).
4. Ставит 3x-ui 3.3.1 с Xray 26.6.1 (версии закреплены, архив сверяется по sha256). Логин, пароль,
   порт и секретный путь панели — случайные. С доменом панель за nginx, без домена — открыта по IP
   (без секретного пути её порт отвечает 404). Без домена скрипт получает сертификат Let's Encrypt на IP
   (с 2026 года их выдают, на ~6 дней): подписка открывается по `https://IP:2096/…`, панель — без
   предупреждения браузера. Продление само, дважды в сутки проверка; 3x-ui перечитывает сертификат без
   перезапуска Xray — VPN у клиентов не рвётся.
5. Создаёт подключение VLESS + XHTTP + Reality (uTLS chrome, xmux) на порту 2083 — с теми же настройками,
   что у основного сервера, — и одного клиента (`--clients N` — больше; остальных удобно добавлять в панели).
6. Настраивает выход клиентов (спросит при установке): напрямую / через Cloudflare WARP / российские
   сайты через WARP / **через другой ваш сервер** (его IP как выход — например старый IP, забаненный
   как вход из РФ, но рабочий как выход). Для последнего скрипт сам заходит на тот сервер по SSH,
   поднимает там вход и прописывает маршрут; если тот сервер упадёт, вотчдог включает запасной режим
   (российские сайты через WARP, остальное напрямую) и возвращает всё обратно, когда он поднимется.
7. BBR, IPv6 выключен, swap 2 ГБ, часовой пояс.
8. **fail2ban:** 5 неудачных входов по SSH за 10 минут — бан на час, повторно — дольше (до недели).
   Адрес, с которого ставили, в исключениях.
9. Фаервол ufw: открыты только SSH и порты VPN. Если на сервере уже работает другой VPN
   (WireGuard, AmneziaWG, Amnezia в Docker), скрипт замечает его и открывает его порты в ufw,
   чтобы не отрубить, и предупреждает (IPv6 на сервере выключается — если тот VPN ходит по IPv6,
   проверьте). Два VPN на одном IP рискованно: заблокируют один — пострадает и другой, надёжнее
   держать их на разных серверах.
10. Команды `vpn-check` и `vpn-warp`; бэкап для переезда — команда `vpn-backup.sh` (сам не запускается).
11. **Проверяет результат:** изнутри — службы, маскировку, подписку и настоящий туннель; снаружи —
    открываются ли SSH и порты VPN из России и Европы, и объясняет, если нет: IP заблокирован,
    порт закрыт у хостера или блокируют только порт.

## Опции

| Опция | Что делает |
|---|---|
| `--domain ДОМЕН` | с доменом, без вопроса (с `CF_API_TOKEN` A-запись в Cloudflare ставится сама) |
| `--no-domain` | без домена, без вопроса |
| `--sni САЙТ` | без домена: под какой сайт маскироваться вместо автовыбора |
| `--no-ip-cert` | без домена: не брать сертификат Let's Encrypt на IP — подписка только внутри сервера (в QR прямые ссылки), панель с самоподписанным сертификатом |
| `--panel-local` | без домена: спрятать панель — только 127.0.0.1 и SSH-туннель (`--panel-public` — снова открыть по IP) |
| `--clients N` | сколько клиентов создать (по умолчанию 1), остальных — в панели |
| `--port N` | порт подключения (по умолчанию 2083). На уже установленном сервере переносит подключение на новый порт: ключи и клиенты те же, старый порт закрывается в ufw; клиентам без подписки — новые ссылки |
| `--exit direct\|warp\|warp-ru\|chain` | выход: с IP сервера (по умолчанию) / всё через Cloudflare WARP (IP сервера не виден сайтам, но бывают капчи Google и потолок около 100 Мбит/с) / российские сайты через WARP / **chain** — через другой ваш сервер (нужен `--exit-host`) |
| `--exit-host IP` | (с `--exit chain`) IP старого сервера-выхода (можно `ubuntu@IP`); скрипт настроит его по SSH. Доступ — пароль root (`EXIT_PASS=…`) или SSH-ключ (`--exit-ssh-key ПУТЬ`, парольная фраза — `EXIT_KEY_PASS=…`); без них скрипт спросит и примет ключ, вставленный целиком. Порт SSH — `--exit-ssh-port`, порт цепочки — `--exit-port` (по умолчанию 2087) |
| `--exit-ssh-user ИМЯ` | (с `--exit chain`) пользователь на старом сервере, по умолчанию root. Не root — настройка через sudo (AWS, Oracle: `ubuntu` с sudo без пароля); если sudo просит пароль — подойдёт пароль входа, `EXIT_SUDO_PASS=…` или скрипт спросит. Если root «пускают» только с подсказкой хостера «Please login as the user "ubuntu"», скрипт сам войдёт под этим пользователем |
| `--exit-stop-xui` | (с `--exit chain`) выключить 3x-ui на старом сервере, если он теперь только выход (`--exit-keep-xui` — оставить) |
| `--ssh-key-only` | выключить вход по паролю (только если у root уже есть SSH-ключ; если вы сами зашли сейчас по паролю — откажется) |
| `--no-fail2ban` | не ставить fail2ban (запоминается; вернуть — `--fail2ban`) |
| `--no-ufw` | не трогать фаервол (запоминается; вернуть — `--ufw`). Перед включением ufw скрипт называет порты, которые сервер слушает и которые фаервол закроет |
| `--tz ЗОНА` | часовой пояс для cron (по умолчанию Europe/Moscow; запоминается) |
| `--skip-dns-check` | не сверять A-запись домена с IP сервера |
| `--skip-ip-check` | не проверять до установки, доступен ли IP из России |
| `--check` | только проверить уже установленный VPN (то же, что `vpn-check`) |
| `--warp off\|on\|ru` | быстро переключить выход без переустановки (то же, что `vpn-warp`) |
| `--bot` | (с доменом в Cloudflare) поставить или обновить Телеграм-бота для управления VPN; токены — `CF_API_TOKEN` и `VPN_BOT_TOKEN` (или спросит), владелец — `VPN_BOT_ADMIN_ID` (или привязка в терминале) |
| `--no-bot` | не ставить бота и не спрашивать про него (запоминается) |

Повторный запуск безопасен: ключи, пароли, клиенты и выбранный вариант сохраняются в `/etc/vpn-install.env`.
Если повторный запуск оборвётся (ошибка, Ctrl-C), база 3x-ui возвращается такой, какой была до запуска, и VPN
работает как работал. Если первая установка не дошла до конца (например, Let's Encrypt не выдал сертификат на
домен), запустите снова — можно и с другим вариантом (`--no-domain`) или другим доменом. На сервер, где 3x-ui уже
стоит не от этого скрипта, он без вашего согласия не ставит (спросит в терминале).

## После установки

- **Приложения** (нужно ядро Xray): iPhone/iPad — Happ, v2RayTun, Streisand; Android — Happ, v2RayTun,
  v2rayNG; Windows/macOS — Happ, v2RayTun, v2rayN. Приложения на sing-box (Hiddify и похожие)
  транспорт XHTTP не умеют.
- **Новые устройства** — в панели: Подключения → клиенты → «+», у каждого своя ссылка.
- **Не работает?** На сервере: `vpn-check`. Ничего не меняет, только проверяет и говорит, в чём дело.
- **Выход через WARP** включается и выключается без переустановки:
  - `vpn-warp off` — WARP выключен целиком, трафик идёт напрямую с IP сервера;
  - `vpn-warp on` — весь трафик через Cloudflare WARP;
  - `vpn-warp ru` — российские сайты через WARP, остальное напрямую;
  - `vpn-warp` — показать, как сейчас.

  После переключения скрипт проверяет настоящий туннель и, если не заработало, возвращает как было.
  Регистрация WARP сохраняется: повторное включение не создаёт новое устройство у Cloudflare.
  Выбранный режим запоминается — повторный запуск установщика его не сбросит.

## Роутер с OpenWrt (PassWall2)

Чтобы VPN работал на весь дом, на роутер с прошивкой OpenWrt 22.03+ ставится PassWall2: в нём ядро Xray, а
оно нужно для XHTTP (Podkop и HomeProxy на sing-box с этим сервером не работают). `install-passwall2.sh` ставит
его одной командой с компьютера — файл в текущей папке, пароль root роутера спросит ssh. Скачать:
`curl -fsSL -o install-passwall2.sh https://raw.githubusercontent.com/Jodc2/vpn-install/main/install-passwall2.sh`

- Mac, Linux: `ssh root@192.168.1.1 sh < install-passwall2.sh`
- Windows (командная строка cmd): `type install-passwall2.sh | ssh root@192.168.1.1 sh`

Скрипт проверяет роутер (OpenWrt 22.03+, от 256 МБ памяти, ~50 МБ свободно), берёт последний выпуск PassWall2 с
GitHub — с русским переводом и ядром Xray под архитектуру роутера — и меняет dnsmasq на dnsmasq-full: без него
PassWall2 не разводит трафик по доменам (настройки DHCP и DNS сохраняются; не встал — возвращается прежний).
Подписку и настройки не трогает: после установки PassWall2 выключен. Повторный запуск обновляет PassWall2.
Проверка — на настоящем OpenWrt 24.10 (opkg) и 25.12 (apk) в контейнерах: `bash test/passwall2.container.sh`.

Дальше — в веб-интерфейсе роутера: «Службы → PassWall2 → Подписки» → «Добавить», ссылку на подписку — в «URL
подписки» → «Сохранить» → «Ручное обновление подписки»; затем «Общие параметры» → «Включить модуль», в «Узел» —
сервер → «Сохранить и применить». Роутеру лучше отдельный клиент (в боте «➕ Добавить», имя «роутер»).

## Телеграм-бот

Если домен лежит в Cloudflare, скрипт предложит поставить Телеграм-бота для управления VPN — бесплатно, на
вашем аккаунте Cloudflare (Workers). Бот умеет: создать клиента (сразу даёт ссылку на подписку), временно
выключить или удалить его, показать статистику, раз в 3 часа проверять, не заблокирован ли IP сервера в
России (Globalping — проверялки у российских провайдеров), каждую ночь сохранять бэкап в хранилище Cloudflare
и переносить VPN на новый сервер кнопкой: вводите IP, логин и пароль нового сервера — бот поднимает там всё из
бэкапа и сам меняет A-запись.

Что понадобится (скрипт спросит в начале установки):
1. Токен Cloudflare — его скрипт спросит первым, вместе с выбором домена (ссылка, где нужные права уже
   отмечены: «Continue to summary» → «Create Token»); второй раз для бота не спрашивает.
2. Токен бота — в Телеграме @BotFather → `/newbot`.
3. Когда скрипт попросит, написать своему боту любое сообщение: так он узнаёт владельца — бот слушается только его.

Без вопросов — токены вставить в скрытый ввод, а не в саму команду (иначе они останутся в истории команд):
`read -rs CF_API_TOKEN; read -rs VPN_BOT_TOKEN; export CF_API_TOKEN VPN_BOT_TOKEN`, затем
`VPN_BOT_ADMIN_ID=<ваш числовой id в Телеграме> bash install-vpn.sh --bot`.
Второй сервер в том же аккаунте Cloudflare — со своим ботом: другой токен от @BotFather и `VPN_BOT_WORKER=vpn-bot2`
(без этого скрипт не отдаст ему бота первого сервера, не спросив).
Не ставить и не спрашивать: `--no-bot`.

- Токены и ключ бота на сервере не остаются — только в секретах воркера в Cloudflare. Токен Cloudflare
  хранится в боте: он нужен для смены A-записи при переезде (по ссылке у него права на воркеры, KV и DNS).
- Повторный запуск не плодит ботов: без токена Cloudflare бот не трогается; с токеном — обновляется код, а
  клиенты, владелец и бэкапы сохраняются. Если повтор меняет домен, выход или порт SSH, скрипт попросит
  токен, чтобы бот узнал новые настройки.
- Не поставился бот (неверный токен, домен не в Cloudflare) — VPN всё равно ставится, а скрипт пишет причину
  и команду повтора.
- При выходе через другой сервер бот при переезде сам открывает на нём порт новому входу, если в этом запуске
  скрипт настраивал выход и sudo там без пароля; иначе бот покажет команду для ручного запуска.

## Выход через другой ваш сервер (chain)

Полезно, когда у вас есть второй сервер, чей IP вы хотите видеть как выход — например старый IP,
заблокированный как вход из России, но рабочий как выход. Новый сервер (вход) и старый (выход)
связываются так: при установке выбираете пункт 4 (или `--exit chain --exit-host IP_СТАРОГО`), скрипт
сам заходит на старый сервер по SSH и настраивает его.

Что нужно: старый сервер — тоже Ubuntu/Debian с доступом root по SSH, доступный новому серверу.
Вход — по паролю или по SSH-ключу: на вопросе выберите «по SSH-ключу» и вставьте ключ целиком
(от `-----BEGIN` до `-----END`, на экране не отображается) или укажите путь к файлу. Подходят ключи
OpenSSH, PEM (`RSA PRIVATE KEY`), PKCS#8 и PuTTY `.ppk`; парольную фразу скрипт спросит. Ключ нигде
не сохраняется: копия с правами 600 живёт только во временной папке установки и удаляется в конце. На старом ставится только лёгкий вход Xray (один порт,
по умолчанию 2087), маскировка под крупный сайт; весь клиентский трафик идёт новый → старый → интернет,
так что сайты видят IP старого сервера.

Если на старом сервере **уже работает 3x-ui** (был прежний VPN) — цепочке это не мешает, обе службы
работают рядом (разные порты). Скрипт это заметит и, если старый теперь только выход, предложит
выключить 3x-ui (или сразу `--exit-stop-xui`). Если старая 3x-ui занимает порт цепочки, скрипт
честно об этом скажет — возьмите другой `--exit-port` или `--exit-stop-xui`.

Надёжность: при установке скрипт заодно регистрирует Cloudflare WARP и ставит вотчдог. Если старый сервер
станет недоступен (4 проверки подряд раз в 30 с, около 2 минут), включается запасной режим: российские сайты
идут через WARP, всё остальное и DNS — напрямую с IP нового сервера. Так IP нового сервера не видят российские
сайты, а если вдобавок ляжет WARP, отвалятся только они. Старый сервер вернулся (3 проверки подряд) — всё
снова через него. Что активно сейчас — `vpn-check` или `vpn-warp`.

Как запасной режим отличает российское: по зонам `.ru`, `.su`, `.рф`; по списку российских сервисов
`geosite:category-ru` из базы Xray (около тысячи доменов: Яндекс, VK, Сбер, Т-Банк, Госуслуги, Озон, ВБ,
2ГИС, Касперский…); и по российским IP-адресам `geoip:ru` — если приложение прислало адрес, а не имя
сайта. Российский сайт на домене вне этого списка (например `.com`), открытый по имени, пойдёт напрямую.

**AWS, Oracle и другие облака.** Там обычно нет входа под root — только `ubuntu` с sudo: скрипт входит под ним
(на вопрос «Пользователь на старом сервере» ответьте `ubuntu`; если оставить root, а хостер подскажет
пользователя, скрипт перейдёт на него сам). Порт цепочки (TCP 2087) там закрыт облачным фаерволом:
откройте его для IP нового сервера — AWS: Security Group, Oracle: Security List или NSG. Правила iptables
самого сервера (у образов Oracle) скрипт открывает сам. Пока порт закрыт — запасной режим (российские сайты через WARP, остальное напрямую), а как
откроете — вотчдог сам переключит на старый сервер.

Переезд входа на другой IP: на старом сервере откройте порт новому адресу
(`ufw allow from НОВЫЙ_IP to any port 2087 proto tcp`) или просто повторите установку с `--exit-host`.

Если попытка настроить старый (или другой) сервер не удалась — неверный пароль, сервер недоступен, —
прежняя цепочка остаётся как была. SSH-ключ старого сервера скрипт запоминает (`/etc/x-ui/chain/known_hosts`)
и при повторной настройке того же сервера сверяет: переустановили старый сервер — удалите этот файл.

## Бэкап и переезд

- Автоматических бэкапов нет. Перед переездом — `vpn-backup.sh`: архив со всеми ключами и клиентами
  ляжет в `/root/backups/` (`latest.tgz` — последний). Забрать к себе: `scp root@IP_СЕРВЕРА:/root/backups/latest.tgz .`
  (вход не под root, как на AWS/Oracle: `ssh ubuntu@IP_СЕРВЕРА 'sudo cat /root/backups/latest.tgz' > latest.tgz`)
- Переезд: на новом сервере `tar xzf архив.tgz && bash vpn-backup-*/restore.sh`. С доменом — потом
  сменить A-запись, клиентам ничего не делать. Без домена — раздать новые ссылки, которые напечатает restore.sh.
- Подробно — README.md внутри архива бэкапа.

## Безопасность

- Секреты — в `/root/vpn-info.txt` (пароль панели), `/etc/vpn-install.env` (ключи Reality) и в архивах
  бэкапа: не пересылать в мессенджеры и не выкладывать. В самом скрипте секретов нет — ключи генерируются
  на сервере при установке.
- Панель: с доменом — только по секретному пути за nginx; без домена — по IP на случайном порту и секретном
  пути (без пути порт отвечает 404, пароль длинный и случайный). Открытый порт панели могут найти сканеры —
  если это важнее удобства, `--panel-local` прячет её за SSH-туннель.
- Безопаснее всего войти на сервер по SSH-ключу и запустить скрипт с `--ssh-key-only`.
- Клиенты VPN не достают до внутренних адресов (127.0.0.1, 10/8, 169.254/16, 192.168/16 и т. п.) ни входного,
  ни старого сервера — ни по IP, ни по имени вроде `localhost`: службы самих серверов (API Xray, панель,
  метаданные облака) через VPN не видны. Секреты цепочки на старый сервер передаются файлом с правами 600 и
  в командную строку процессов не попадают.

## Как проверялся и чего не знает

- Прогнан в контейнерах Ubuntu 22.04, 24.04 и Debian 12: оба варианта (с доменом и без), WARP,
  выход через другой сервер (установка по SSH; переключение вотчдога в запасной режим и обратно —
  с проверкой, что российский сайт идёт через WARP, когда прямой доступ к нему закрыт),
  повторный запуск, переезд из бэкапа (в том числе со сменой IP), бан fail2ban при настоящем подборе
  пароля; обрыв посреди повторного запуска (база возвращается), неудачная смена сервера-выхода (цепочка
  остаётся), смена варианта после неудачной первой установки, запрос `localhost` через туннель (закрыт). Выпуск сертификата — на живом сервере через тестовый Let's Encrypt. Полностью на свежем VPS
  с боевым Let's Encrypt — ещё нет.
- Выход через другой сервер в контейнерах шёл через общий NAT, поэтому IP выхода там не отличить;
  что трафик реально идёт через старый сервер, проверено так: при остановке входа на старом сервере
  туннель сразу перестаёт работать, при запуске — снова работает.
- Проверка блокировки опирается на check-host.net, у которого в России сейчас два узла, оба в московских
  дата-центрах: блокировку у отдельных провайдеров (например, мобильных) она может не увидеть.
